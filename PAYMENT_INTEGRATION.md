# TovarkaDuck — ручна оплата переказом на картку

## 1. Що це і чого це НЕ є

Це реалізація **ручної оплати переказом**, а не автоматичного інтернет-еквайрингу.
Немає жодного зовнішнього платіжного API (Monobank/LiqPay/WayForPay). Гроші
переказує сам покупець зі свого банківського застосунку на вказану картку,
а факт оплати підтверджує людина (адмін), переглянувши прикріплений
скріншот. Система НЕ перевіряє автоматично, чи гроші реально надійшли.

Якщо пізніше знадобиться справжня автоматична онлайн-оплата — знадобиться
окрема інтеграція з API одного з еквайрингів (Monobank/LiqPay/WayForPay) із
реальними merchant credentials, яку раніше вже обговорювали в цій розмові.

## 2. Способи оплати в checkout

| Значення `paymentMethod`      | Опис                                              |
|--------------------------------|----------------------------------------------------|
| `CASH_ON_DELIVERY`             | Накладений платіж, оплата при отриманні            |
| `CARD_TRANSFER_FULL`           | Переказ повної суми замовлення, зі скріншотом      |
| `CARD_TRANSFER_PREPAYMENT`     | Переказ фіксованої передоплати, решта — при отриманні |

Сума передоплати визначається сервером через
`CARD_TRANSFER_PREPAYMENT_AMOUNT` (або `NEXT_PUBLIC_CARD_TRANSFER_PREPAYMENT_AMOUNT`,
якщо перша не задана) — **не клієнтом**.

## 3. Статус оплати (`paymentStatus`)

| Статус     | Коли встановлюється                                             |
|------------|-------------------------------------------------------------------|
| `UNPAID`   | За замовчуванням; для накладеного платежу лишається таким         |
| `PENDING`  | Клієнт обрав онлайн-переказ і прикріпив скріншот при створенні    |
| `PAID`     | Адмін вручну підтвердив оплату в адмін-панелі                     |
| `FAILED`   | Адмін відхилив скріншот / оплату не підтверджено                  |
| `REFUNDED` | Зарезервовано на майбутнє (ручне повернення коштів), поки не використовується в UI |

**Ніхто, крім адміна через `PATCH /api/orders/:id/payment`, не може встановити `PAID`.**
Звичайний `PATCH /api/orders/:id` (зміна статусу виконання замовлення) навмисно
не приймає `paymentStatus` у тілі запиту.

## 4. Захист від подвійного підтвердження

`PATCH /api/orders/:id/payment`:
- вимагає admin JWT (`requireAdmin`);
- якщо `paymentMethod === CASH_ON_DELIVERY` — повертає 400 (нема що підтверджувати);
- якщо `paymentStatus` вже `PAID` або `FAILED` — повторний виклик **нічого не змінює**
  і повертає поточне замовлення без помилки (ідемпотентність, захист від
  подвійного натискання кнопки чи повторного запиту).

## 5. Обмеження зберігання скріншота

Скріншот зберігається як **base64 data URL прямо в PostgreSQL** (`Order.paymentScreenshotUrl`,
тип `Text`). Це найпростіший варіант, що працює без додаткової інтеграції
файлового сховища, але має мінуси:
- збільшує розмір бази даних;
- максимум ~2 МБ на скріншот (обмежено в `orderCreateSchema`), клієнт стискає
  через `<input type="file">` без додаткового стиснення.

**Рекомендація на майбутнє:** перенести зберігання на Vercel Blob, S3 або
Cloudinary, а в `paymentScreenshotUrl` зберігати лише посилання. Я свідомо
не додав це зараз, щоб не вводити нову зовнішню залежність без твого дозволу.

## 6. Кроки впровадження (зроби в такому порядку)

1. Забери файли з цієї розмови та заміни ними відповідні файли в
   `Vitalik15072009/tovarka.duck` (шляхи співпадають один в один):
   - `prisma/schema.prisma`
   - `src/lib/validation.ts`
   - `src/lib/serializeOrder.ts` (новий файл)
   - `src/types/index.ts`
   - `src/app/api/orders/route.ts`
   - `src/app/api/orders/[id]/route.ts`
   - `src/app/api/orders/[id]/payment/route.ts` (новий файл + нова папка `payment/`)
   - `src/app/api/user/orders/route.ts`
   - `src/app/checkout/page.tsx`
   - `src/app/admin/orders/page.tsx`
   - `.env.example`

2. Додай нові змінні у `.env` (локально) та у Vercel Environment Variables:
   ```env
   NEXT_PUBLIC_CARD_TRANSFER_NUMBER=твій номер картки
   NEXT_PUBLIC_CARD_TRANSFER_HOLDER=ПІБ отримувача
   NEXT_PUBLIC_CARD_TRANSFER_PREPAYMENT_AMOUNT=150
   ```

3. Встанови залежності та згенеруй Prisma client:
   ```bash
   npm ci
   npx prisma generate
   ```

4. Створи міграцію (додає enum `PaymentStatus` і нові nullable-поля в `Order`,
   нічого не видаляє й не змінює тип існуючих колонок):
   ```bash
   npx prisma migrate dev --name add_manual_payment_review
   ```

5. Запусти build і виправ усе, що покаже TypeScript/Next.js:
   ```bash
   npm run build
   ```
   Я не мав мережевого доступу до твого репозиторію та npm-реєстру в своєму
   середовищі, тому **не запускав build сам**. Якщо він покаже помилки —
   скинь мені повний текст помилки, я одразу виправлю відповідний файл.

6. Перевір локально (`npm run dev`):
   - оформи замовлення з накладеним платежем → `paymentStatus = UNPAID`, все як раніше;
   - оформи замовлення з "Переказ на картку" без скріншота → кнопка заблокована;
   - прикріпи скріншот → замовлення створюється, `paymentStatus = PENDING`;
   - зайди в адмінку → побач картку, спосіб оплати, статус, скріншот;
   - натисни "Підтвердити оплату" → статус стає `PAID`, повторне підтвердження нічого не міняє;
   - натисни "Відхилити" на іншому замовленні → статус `FAILED`.

7. **Не переходь до інтеграції Нової Пошти**, поки цей build не проходить
   без помилок і ручний флоу оплати не протестований у dev-режимі.

## 7. Що я НЕ зробив і чому

- Не викликав жодного платіжного API (Monobank/LiqPay/WayForPay) — за твоїм
  явним рішенням користуватись ручним переказом.
- Не змінив логіку списання товару зі складу — вона і раніше списувала
  залишки одразу при створенні замовлення, незалежно від оплати. Це вже
  існуюча поведінка репозиторію, я її не чіпав, щоб не зламати інвентаризацію.
  Якщо хочеш, щоб залишки списувались лише після підтвердження оплати —
  скажи окремо, це самостійна зміна.
- Не додав зовнішнє файлове сховище для скріншотів (див. розділ 5).
